# 青禾集市（c2c）优化路线

> 制定时间：2026-10-29
> 输入：《项目分析与优化建议.md》（问题编号 S*/C*/P-*/E* 均出自该文，本文不重复描述问题本身）
> 定位：把「问题清单」翻译成「可执行、可验收、可回滚」的分阶段计划。单开发人员、业余时间假设，每阶段独立交付、独立可验证。
> 不做什么：暂不做微服务拆分（伪 Feign 更名即可，见 M3）、不上 ES/消息队列中间件、不改技术栈主线（Spring Boot 2.7 → 3.x 的升级单列在 M5 之后评估）。

---

## 1. 路线总览

```
M1 安全加固 ──► M2 交易正确性 ──► M3 工程化 ──► M4 体验与性能 ──► M5 生产化
  1~2 周          1 周             1~2 周         3~4 周           4~8 周（依赖商户资质）
```

| 里程碑 | 目标 | 关键交付 | 验收标准 | 依赖 |
|---|---|---|---|---|
| M1 安全加固 | 堵上所有可被低成本利用的口子 | S1/S2/S3/S4/S5/S7 修复 + C1/C4/C5/C6 | 复核清单全过 + 越权/爆破/回显测试用例通过 | 无 |
| M2 交易正确性 | 订单状态机收敛为真实流转 | balance 支付改托管（status=1），ship/receive 可达，删除死代码 | 全流程手工用例 8 条通过 | M1 的 S2 |
| M3 工程化 | 可回归、可交接 | 核心单测 ≥15 个、CI 流水线、README/SQL 文档对齐 | CI 绿灯、新成员按 README 可 30 分钟跑起 | M2（状态机稳定后再固化测试） |
| M4 体验与性能 | 三大前端体验与后端资源占用明显改善 | 图片缩略图+OSS/或本地多尺寸、浏览量削峰、WebSocket IM | 首屏图片流量降 ≥60%；IM 端到端延迟 <1s；压测报告 | M3 的 CI（防回归） |
| M5 生产化 | 具备真实上线条件 | 支付宝/微信沙箱支付、HTTPS 域名、种子口令治理、（可选）JDK17+SB3 升级评估报告 | 支付回调验签+幂等测试通过；域名全站 HTTPS | M2 的状态机是硬依赖 |

> 时间均为单人业余投入估算；若作为毕业设计推进，M1–M3 应压缩在 4~6 周内完成（与《毕业设计完善路线.md》对齐）。

## 2. M1 安全加固（1~2 周）

### 2.1 任务分解（按实施顺序）

| # | 任务 | 问题编号 | 改动点 | 工作量 | 验证 |
|---|---|---|---|---|---|
| 1.1 | 验证码回显开关默认值修正 | S1 | `application.yml` 改 `false`；`application-test.yml` 显式 `true`；核对 `config/application-prod.yml` 不覆盖该 key | 0.5h | 生产配置启动，抓包登录响应无 code；test 配置回显 |
| 1.2 | 管理员登录失败锁定 | S3 | 复用 `checkLoginLock/failLoginLock` 模式（抽公共组件或直接在 AdminAuthController 用 Redis 计数：15 分钟 5 次） | 0.5h | 连错 5 次锁 15 分钟；锁定期间正确密码也拒绝 |
| 1.3 | 评价接口订单校验 | S2 | `RatingService.submit`：查订单→校验评价人∈买卖方→status=4→角色与身份匹配；按 (orderId, raterId) 已有唯一索引兜底 | 0.5h | 非订单双方提交 403；未完成订单评价被拒；正常互评通过 |
| 1.4 | refreshToken 隔离 | S4 | 签发加 `type=refresh` claim；新增 `POST /user/refresh`；过滤器拒绝 type=refresh 的业务请求；改密/注销删 Redis | 0.5~1h | refresh token 访问业务接口 401；/user/refresh 换发成功 |
| 1.5 | token 版本化 | S5 | user 表加 `token_version`；登录写入 claim；过滤器比对库值；封禁/改密/角色变更/权限调整时递增 | 1~2h | 改密后旧 token 立即失效；封禁用户 token 失效 |
| 1.6 | 微信 mock 加闸 | S7 | mock=true 且 profile=prod 拒绝启动；非 prod 打印醒目 WARN | 0.5h | prod+mock=true 启动失败 |
| 1.7 | 地址快照序列化 | C1 | `buildAddressSnapshot` 改 `objectMapper.writeValueAsString` | 0.5h | 收货人名含 `"` 时订单详情正常解析 |
| 1.8 | 订单号与锁表 | C4/C5 | 后缀改 `SecureRandom`（8 位）；`order_no` 加唯一索引 + 冲突重试；`LOCKS` 改 `Striped<Lock>`（64 条） | 1h | 同毫秒并发 100 单号无重复；锁表大小恒定 |
| 1.9 | 入参边界校验 | C6 | `ProductCreateDTO` 加 `@DecimalMin/@Size`；顺带检查 RegisterDTO/LoginDTO/CommentCreateDTO | 0.5h | 负数价格、201 字标题被拒 |

### 2.2 M1 验收清单

- [ ] 复核脚本：S1–S7 全部在源码中确认修复（更新《安全修复待办清单.md》状态）
- [ ] 安全回归用例（越权评价、爆破锁定、refresh 混用、验证码回显）4 条手工通过
- [ ] `mvn clean package -DskipTests` 通过；前端 lint/build 通过
- [ ] 数据库迁移脚本：仅 `token_version` 字段（并入 `init.sql` 并给出现有库的 ALTER 语句，遵循 sql/README.md 规范）

### 2.3 风险

- 任务 1.5（token 版本化）会**强制所有在线用户重新登录**，需在公告/前端给出友好提示；建议与 1.4 同批上线，只打扰一次。
- 任务 1.8 的唯一索引：历史数据若已有重复 order_no 需先清洗（当前生成规则下概率极低，先跑 `SELECT order_no, COUNT(*) ... GROUP BY HAVING COUNT>1` 确认）。

## 3. M2 交易正确性（1 周）

### 3.1 目标状态机

```
0 待支付 ──pay()──► 1 已支付(escrow=amount) ──ship()──► 2 已发货 ──receive()──► 4 已完成(打款卖家)
   │                                                    │
   └──cancel()──► 5 已取消(未支付直接取消/已支付走退款) ◄──┘ (卖家未发货前)
```

改动点（`OrderServiceImpl`）：

| # | 任务 | 对应问题 | 说明 |
|---|---|---|---|
| 2.1 | `pay()` 不再自动完成 | C3 | 扣款后 `escrow=totalAmount, status=1`，删自动发货/收货代码 |
| 2.2 | 删除 cancel 恒真判断 | C2 | `setStatus(5)` 后按原状态决定动作（status=1 需退款） |
| 2.3 | 前端联调 | — | 订单详情页按 status 渲染操作按钮（1→卖家发货、2→买家收货）；管理端订单状态文案对齐 |
| 2.4 | 超时关单兜底 | — | 现状 `publishOrderTimeout` 事件无消费者则超时订单永远滞留；增加定时任务（每 5 分钟扫描 status=0 且 created_at<now-30min 关单并恢复商品） |

### 3.2 验收清单

- [ ] 手工用例：下单→支付→发货→收货→评价（买卖双方）全链路通过；取消分支（未支付/已支付）通过
- [ ] 托管金额方向核对：钱包流水 recharge/pay/refund/receive 与订单状态一一对应（对账 SQL 抽查 3 单）
- [ ] 超时关单：造一笔 31 分钟前的待支付订单，定时任务执行后 status=5、商品回到在售

## 5. M4 体验与性能（3~4 周）

| # | 任务 | 对应问题 | 要点 |

| 4.1 | 图片多尺寸 + 对象存储 | P-b/P-d | 上传时生成 200/400/800 三档；列表用 200、详情用 800；OSS/COS + 预签名直传（本地磁盘方案保留为 fallback） |

| 4.5 | 压测基线 | — | JMeter：首页列表/详情/登录/下单 4 接口，100 并发各 5 分钟，产出基线报告（作为 M4 与毕设的共同素材） |

- [ ] 首页图片总流量下降 ≥60%（DevTools 对比）
